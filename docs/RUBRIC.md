# 계획서 채점 루브릭 (사전 공개본 · 고정)

> 이 문서는 계획서(`docs/PLAN.md`) 작성 **전에** 고정한다. 채점 중 기준을 완화하지 않는다.
> 채점자는 작성자와 다른 에이전트여야 한다. 통과 조건: **모든 항목 ≥ 90/100 이고 평균 ≥ 95/100**.

## 채점 원칙
- 각 항목 0~100점. 앵커: **100** 결함 없음·근거 완비 / **90** 사소한 표현 문제만 / **75** 검증 가능하지만 근거·구체성 1건 부족 / **50** 중대 누락 1건 / **25 이하** 항목 자체가 형식적.
- 근거 없는 수치·사실 주장은 그 항목에서 **-15점** (출처 URL 또는 `[확인]/[추정]/[데이터공백]` 태그가 없으면 근거 없음으로 본다).
- "TODO"·"추후 결정" 같은 빈칸이 있으면 해당 항목 최대 70점.
- 채점자는 항목마다 **점수 · 근거(계획서의 어느 줄) · 미달 사유 · 시정 지시**를 적는다. 시정 지시는 한 줄로 실행 가능해야 한다.

## 항목

| # | 항목 | 무엇을 보는가 |
|---|---|---|
| 1 | 목표·범위 | 한 문장 목표, 1차 범위와 **범위 밖을 긍정형으로** 명시. MVP가 영상 범위(수집·스냅샷·조건 필터·배포)와 일치하는가. |
| 2 | 데이터 출처·API 규격 근거 | 엔드포인트·파라미터·응답 필드·호출 한도·승인 방식이 출처 URL과 함께 적혀 있는가. 확인/추정/공백 태그가 붙어 있는가. |
| 3 | 아키텍처 적합성 | 스냅샷 1회 수집 → 정적 필터링 → 정적 배포 구조가 API 제약(서버 조건검색 불가·일 1만 건)과 논리적으로 맞는가. 인증키가 배포물에 들어갈 경로가 없음이 설계로 보장되는가. |
| 4 | 요구사항 추적성 | Manyfast 요구사항(R-)·기능(F-)·스펙(S-) ID가 계획의 작업 단위와 1:1 또는 N:1로 매핑된 RTM이 있는가. 1차 범위 밖 ID는 명시적으로 제외 처리됐는가. |
| 5 | 함정 대응 설계 | 기업 사업 유입 · 건수 불일치 · 지역 누락 · 인증키 한쪽만 실패, 4가지 각각에 **구체 규칙(어느 필드를 어떤 값으로 판정)**과 검증 방법이 있는가. |
| 6 | 수용기준 검증가능성 | 수용기준이 EARS 형식(When/If … the system shall …)이고 각 기준에 **재현 명령 또는 조작 절차와 기대 출력**이 붙어 있는가. |
| 7 | 실행 계획 구체성 | 파일 목록(경로·역할), 작업 순서, 각 단계의 명령이 복붙 가능한가. 의존성(키 없을 때 샘플 데이터 경로)이 처리됐는가. |
| 8 | 리스크·가정·데이터공백 | 인증키 미보유, 미결 결정(Manyfast 질문 22건)의 처리 방식, API 변경 가능성이 표로 정리되고 각각 대응이 있는가. 없는 것을 있다고 쓰지 않았는가. |
| 9 | 검증·오류점검 계획 | 단위/통합/수동 검증 방법, 배포 후 인증키 부재 검사 절차(명령 포함), 모바일 확인 절차, 실패 시 롤백이 있는가. |
| 10 | 비개발자 실행 가능성 | 사용자가 따라 할 절차가 한글·복붙 단위·순서대로이고, 본인만 할 수 있는 단계(계정·키 발급·로그인)가 분리 표기됐는가. |

## 산출 형식 (채점자)
```
| # | 점수 | 근거(줄) | 미달 사유 | 시정 지시 |
평균: NN.N
판정: PASS / FAIL
```
